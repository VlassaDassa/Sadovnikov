## TYPOGRAPHY

Файл: `typography.scss` / токены типографики.

Управление типографикой: шрифт, начертание, размер, высота строки, цвет — через отдельные стили / классы.

Изначально идея была в том, чтобы в одном месте описать типографику из дизайн-системы и потом собирать текст не вручную в каждом компоненте, а из заранее подготовленных вариантов.

Размеры в основном завязаны на `rem`, поэтому глобальный размер `html` в какой-то момент тоже являлся частью адаптива.

### Исключения

Когда необходимо переопределить какой-то параметр класса, раньше я активно использовал `@extend`.

Из-за этого постепенно появилась проблема: система хорошо выглядит пока всё совпадает с дизайн-системой один в один, но как только нужен отдельный адаптивный случай — начинается борьба с наследованием.

UPD: сейчас я бы меньше строил систему вокруг `@extend`. Токены оставить точно стоит, а вот саму реализацию типографики можно сделать проще. В какой-то момент я пытался слишком сильно заставить SCSS работать как отдельный UI-фреймворк.

## BUTTON

Папка: `button`.

В проекте есть обычная кнопка и декоративная кнопка. Вариаций достаточно много, потому что дизайн кнопок делался отдельно в Figma.

Дизайн-система:

https://www.figma.com/design/qYYGvs1TraAVy6K7T8sjwO/Portfolio?node-id=118-309&t=TDitP6gfY2icaRyS-1

### Размеры кнопок

Изначально кнопке задавался размер, но он мог адаптироваться через `useBreakpoint`, который определял `mobile / tablet / desktop`, после чего это уже переводилось в `big / medium / small`.

Почему так?

Это можно было сделать в SCSS, но в тот момент вся типографика и размеры уже были построены вокруг генерации классов и наследования. `@extend` внутри media query нормально не решал задачу, а переделывать всю систему под mixin тогда не хотелось.

Плюс казалось, что `useBreakpoint` в будущем пригодится ещё в куче мест.

### UPD 1

`useBreakpoint` был удалён после переезда на Next.js.

Тут у меня в старом README даже формулировка была кривая: я писал, что компонент «становился серверным». Наоборот — из-за клиентского хука компонент приходилось переводить в Client Component.

Для компонента, которому от JS нужен только размер экрана, это довольно дорогая причина тащить client boundary.

Тогда часть адаптива была просто перенесена в SCSS.

### UPD 2

Breakpoint позже опять вернулся, но уже централизованно через Redux Toolkit.

Почему?

Оказалось, что есть места, где breakpoint нужен не только для CSS, а реально влияет на логику / отображаемую структуру. Считать его отдельно в нескольких компонентах было глупо.

Поэтому идея стала такая: если JS-breakpoint всё-таки нужен — вычислять его в одном месте и уже раздавать дальше.

Сейчас я бы ещё раз очень внимательно проверил, где breakpoint действительно нужен в JS, а где можно оставить всё браузеру и CSS.

### Поведение

`hover` — через SCSS.

`default / loading / disabled` — через параметры компонента.

После тестов это место тоже пришлось поправлять: loading-кнопка не должна оставаться фактически кликабельной. То есть визуальный loading недостаточен, состояние должно реально блокировать повторное действие.

### Исключения

По дизайну иногда нужен длинный текст, который физически не помещается в самый маленький вариант декоративной кнопки.

Для этого появился `decorativeBtnText`: основной текст + запасной вариант для мобильной версии.

Не идеальная универсальность, но конкретную дизайн-задачу решает.

## ICONS

Папка: `icons`.

Есть общий компонент `Icon`, а конкретные SVG вынесены в отдельные компоненты `Icon[Название]`.

Внутри общего компонента выбирается нужная иконка.

Почему так?

Хотелось единообразно прокидывать размер / цвет и не импортировать SVG-реализации хаотично по всему проекту.

Система получилась достаточно простой и, в отличие от некоторых других моих абстракций, до сих пор меня особо не раздражает.

## IMPORT / DYNAMIC IMPORT

Некоторые импорты после переезда на Next.js пришлось пересмотреть из-за Server / Client Components.

Раньше у меня были отдельные компоненты с названием вроде `DynImport...`.

UPD: сейчас я бы меньше думал в терминах «как любой ценой сохранить компонент серверным» и больше — где проходит нормальная граница ответственности.

## TOOLTIP

Вызов через кастомный хук `useTooltip`.

В него передаются настройки, а он возвращает `ref`, который привязывается к элементу.

В layout есть глобальный Tooltip.

Есть несколько уровней:

- `lvl1` — просто текст;
- `lvl2` — заголовок + текст;
- `lvl3` — заголовок + дата + текст.

Также есть `placement`: `bottom / right / left / top`.

Смысл всей этой замудрённой системы был в том, чтобы tooltip показывался около элемента, не вылезал за viewport и не перекрывал то, что не надо.

### fakeWidth

Был параметр `fakeWidth` — примерная предполагаемая ширина tooltip.

Почему не измерять идеально на лету?

Потому что в тот момент для этого пришлось бы заметно перестраивать уже написанную архитектуру. Для обычной подсказки условных `100`, а для длинного stack/evolution tooltip — условных `400` хватало.

И да, это компромисс.

Сейчас я бы, скорее всего, сначала посмотрел в сторону нормального positioning engine / Floating UI, прежде чем писать ещё один слой собственного позиционирования.

Но именно на этом компоненте я хорошо понял, сколько мелких проблем появляется у штуки, которая визуально выглядит как «просто маленький прямоугольник рядом с кнопкой».

## VISIT ГРАФИК / ANALYTICS

Сначала для графика посещений использовались моковые данные.

Старая заметка была примерно такая:

```env
ANALYTICS_USE_MOCK=true
```

И в admin можно было подмешать `createMockVisits(...)`, чтобы спокойно верстать график без реальной статистики.

Потом аналитика стала реальной и появилась интеграция с Umami.

Почему Umami?

Мне для портфолио не нужен огромный аналитический комбайн. Нужны посещения и данные для собственного dashboard, при этом хотелось нормальную отдельную аналитику, которую можно контролировать.

В тестовом окружении Umami намеренно не является критической зависимостью. Во время E2E может не быть `UMAMI_WEBSITE_ID`, но отсутствие аналитики не должно ломать публичный сайт и тесты основной функциональности.

## ПЕРЕЕЗД НА NEXT.JS

Наверное, самое большое изменение проекта.

Сайт начинался гораздо ближе к обычному React-приложению. В какой-то момент стало понятно, что я хочу не просто красивую страницу, а нормальные страницы проектов, серверную часть, SEO, локализацию, админку и дальше всё это обслуживать как одно приложение.

В итоге переехал на Next.js.

Переезд был не в стиле «поменял Vite на Next и всё заработало».

Начали всплывать:

- Server / Client Components;
- другая работа с layout;
- routing;
- metadata;
- server-only код;
- dynamic import;
- работа с изображениями;
- auth;
- серверные действия;
- кеширование / revalidate;
- различия dev и production build.

Плюс часть моей старой компонентной системы изначально вообще не проектировалась под такую модель.

Поэтому некоторые решения пришлось сначала сломать, потом собрать заново.

Это как раз хорошо видно по веткам и истории коммитов.

## SERVER COMPONENTS / CLIENT COMPONENTS

После миграции я первое время слишком сильно пытался сохранить как можно больше Server Components.

Из-за этого иногда появлялась странная архитектура: отдельная client-обёртка ради маленького хука, динамический импорт, ещё одна прослойка.

Сейчас подход проще:

Если компонент:

- читает данные на сервере;
- не использует состояние;
- не использует эффекты;
- не зависит от browser API;

то пусть остаётся серверным.

Если ему реально нужна интерактивность — делаю Client Component и не пытаюсь выиграть войну за каждую директиву `"use client"`.

Главное — не поднимать client boundary выше, чем реально нужно.

## DATA / POSTGRESQL / PRISMA

Следующий большой этап — уход от моковых данных к базе.

Появился PostgreSQL + Prisma.

В базе теперь живёт не только условный `Project`, а связанные сущности: изображения, stack, key features, description blocks, metrics, commits/evolution и другие данные сайта.

Почему Prisma?

На момент добавления БД мне хотелось не писать вручную большой слой SQL и одновременно нормально чувствовать типы в TypeScript.

Плюс migrations и понятная schema сильно упростили развитие проекта.

### Что вскрылось позже

Очень легко написать mapping, который «на глаз правильный», но теряет одно локализованное поле или неправильно пересоздаёт relations.

Именно integration/server tests потом нашли несколько таких ошибок.

Например:

- терялись `textRu / titleRu`;
- commits при update могли не удаляться перед созданием новых;
- часть локализованных полей сохранялась не туда;
- order нужно было задавать последовательно.

До тестов это было неприятно заметить, потому что happy path визуально работал.

## TRANSACTIONS

Когда админка начала заменять целые наборы данных (`skills`, `stack`, footer и т.д.), сначала логика была в духе:

1. удалить старое;
2. создать новое.

Проблема очевидная уже сейчас: если между пунктами всё падает, данные остаются в промежуточном состоянии.

Поэтому такие операции были перенесены в `prisma.$transaction`.

Это тот случай, где тесты не просто «проверили код», а заставили ещё раз посмотреть на саму модель операции.

## AUTH / BETTER AUTH

Когда появилась админка, оставлять `/admin` просто скрытой ссылкой было очевидно бессмысленно.

Для авторизации используется Better Auth + Prisma/PostgreSQL.

Есть login и серверная проверка доступа.

Главное правило: защита не должна существовать только на уровне UI.

То есть недостаточно спрятать кнопку или сделать redirect в клиенте. Server actions, admin routes и операции с файлами тоже должны проверять авторизацию.

Тесты потом отдельно проверяли, что anonymous пользователь не получает admin page и что server action действительно сначала требует admin.

### UPD

В одном из action'ов у меня вообще был `requireAdmin()` без `await`.

Визуально это очень легко пропустить.

Тест поймал.

## UPLOADS

Загрузка изображений оказалась намного больше, чем «получить File и сохранить».

Появились отдельные вещи:

- корневая папка upload;
- публичный prefix;
- лимит размера;
- категории изображений;
- привязка к project id;
- проверка, что путь относится к управляемым upload;
- защита от path traversal;
- обработка изображения через Sharp;
- SVG sanitization;
- удаление старых файлов;
- сохранение project image.

Почему это всё отдельно?

Потому что файлы — это граница между приложением и файловой системой. Здесь лучше написать чуть больше скучного кода, чем потом обнаружить, что пользовательский путь можно подсунуть куда угодно.

Отдельно был смешной баг в env-переменной:

`UPLOAD_MAX_IMGE_BYTES`

вместо

`UPLOAD_MAX_IMAGE_BYTES`.

С одной буквой меньше половина fallback-логики работала не так, как ожидалось.

## CONTACT FORM / MAIL

Контактная форма сначала была просто клиентской формой.

Потом появилась серверная отправка почты и отдельно вылезла проблема: client validation и server validation должны описывать один контракт.

В какой-то момент клиент принимал длину имени примерно `2–49`, а сервер — вообще другой диапазон.

Форма визуально считала значение нормальным, потом сервер его отвергал.

После этого я стал намного осторожнее относиться к одинаковой validation-логике на двух сторонах.

Ещё была ошибка, когда поля очищались даже после неуспешной отправки.

Тоже классическая мелочь, которую пользователь замечает сильнее, чем разработчик.

## I18N

Публичная часть работает на русском и английском.

Для локализации используется `next-intl`, плюс часть сущностей в БД содержит обычные и `Ru` поля.

Это решение не самое идеальное с точки зрения масштабирования на десять языков.

Но у проекта задача — RU/EN, а не международная CMS.

Поэтому отдельные `title / titleRu`, `text / textRu` здесь достаточно прагматичны.

Если языков станет больше — такую модель я бы уже не расширял `titleDe`, `titleFr`, `titleEs` и т.д. Тогда нужна была бы отдельная модель переводов / JSON-структура / CMS-подход.

## PROJECT EVOLUTION / GITHUB / GIGACHAT

У проекта есть блок evolution / commits.

Изначально это были просто вручную заполненные этапы.

Потом появилась идея подтягивать историю GitHub и на её основе помогать формировать milestones.

Отсюда появились:

- contract с GitHub API;
- работа с commit SHA;
- schema для draft;
- schema ответа GigaChat;
- `sourceShas`, чтобы milestone не существовал совсем «из воздуха»;
- отдельная валидация с Zod.

Почему я вообще это добавил?

Потому что вручную писать красивую историю развития проекта после сотен коммитов довольно уныло.

Но полностью отдавать это LLM тоже не хотелось.

Поэтому идея: модель предлагает структуру, а данные всё равно должны быть привязаны к реальным commits, после чего результат можно проверить / поправить.

## ZOD / VALIDATION

Чем больше появлялось server actions и внешних данных, тем меньше хотелось верить объекту просто потому что TypeScript сказал, что у него есть тип.

TypeScript заканчивается во время runtime.

Поэтому там, где данные приходят извне / от пользователя / от API, появились runtime schema через Zod.

Особенно это важно для GigaChat / GitHub / форм и подобных границ.

## TESTING

Вот здесь я очень долго вообще не хотел упарываться.

Не потому что считаю тесты бесполезными, а потому что для pet-проекта можно бесконечно строить инфраструктуру вместо самого продукта.

В итоге тестирование всё-таки добавил уже когда проект стал достаточно большим.

И сделал несколько уровней:

### unit / component

Быстрые вещи:

- функции;
- reducers;
- hooks;
- небольшие UI-компоненты.

Без реальной БД и сети.

### server

Server actions, auth, routes, upload logic, mail и т.д.

В основном нужны для control flow: validation, authorization, mutation, error handling.

### integration

Здесь уже настоящая PostgreSQL.

Почему не мокать всё?

Потому что как раз mapping / relations / transaction — это те места, где красивый mock может подтвердить код, который с реальной БД работает неправильно.

### E2E

Playwright поднимает production build и проходит реальные пользовательские сценарии в Chromium.

Я специально не стал превращать E2E в проверку каждой кнопки. Они дорогие и медленные.

Задача — проверить большие сценарии.

### accessibility

Автоматические проверки через axe.

Это не означает «сайт теперь полностью доступный». Автоматикой невозможно проверить всё.

Но очевидные нарушения она ловит.

## VISUAL TESTS

Добавлял screenshot regression.

Потом удалил.

Почему?

В теории всё красиво: поменял CSS — screenshot diff показал изменение.

На практике для моего проекта началась возня с baseline между Windows и Linux, разницей fullPage/viewport, окружением CI и поддержкой этих эталонов.

В какой-то момент я потратил больше времени на то, чтобы тестировать сам visual test, чем он давал пользы.

Для продукта, где pixel-perfect regression критичен, я бы это оставил.

Для этого портфолио — нет.

Удалил осознанно.

## LIGHTHOUSE

Тоже был.

Тоже удалил.

Lighthouse полезный инструмент, но делать его blocking gate в этом проекте оказалось сомнительно.

Оценка зависит от окружения и даёт шум, а performance я всё равно могу проверять отдельно, когда реально занимаюсь performance.

Не хочу держать инструмент только ради красивой строки «у меня есть Lighthouse CI».

## K6

Добавлял load test на публичные страницы.

Потом убрал.

Причина примерно та же.

У проекта нет такой нагрузки и такого SLA, чтобы постоянно поддерживать отдельный load-testing слой.

Плюс k6 нельзя бездумно гонять по production.

Если когда-нибудь появится конкретная задача по нагрузке — вернуть несложно.

## CI

После того как тесты стали зелёными локально, стало бессмысленно оставлять их просто набором команд, которые я «должен не забыть запустить».

Поэтому появился GitHub Actions.

На PR CI:

1. поднимает PostgreSQL;
2. устанавливает зависимости;
3. генерирует Prisma Client;
4. валидирует schema;
5. применяет migrations;
6. seed;
7. lint;
8. typecheck;
9. unit/component;
10. server tests;
11. integration;
12. build;
13. Chromium E2E.

Почему CI прогоняет настоящую БД?

Потому что integration tests без неё теряют смысл.

## CD / DEPLOY

Раньше deploy существовал отдельно и запускался просто на `push` в `main`.

И это была плохая схема:

```text
push main
├── tests
└── deploy
```

Т.е. теоретически deploy мог уже поехать на сервер, пока тесты ещё падают.

Потом переделал:

```text
main
  ↓
test
  ↓
deploy
```

`deploy` зависит от успешного job `test`.

Плюс PR в `main` защищён required checks.

Итоговая логика:

```text
feature branch
      ↓
PR
      ↓
tests
      ↓
green?
  ├─ no  → merge blocked
  └─ yes → merge
              ↓
             main
              ↓
            tests
              ↓
            green?
          ├─ no  → no deploy
          └─ yes → production
```

Вот после этого уже считаю, что в проекте реально есть CI/CD, а не просто файл `.github/workflows/*.yml`.

---

## DOCKER / PRODUCTION

Production собирается через Docker.

Отдельно PostgreSQL.

В compose у БД есть healthcheck, а приложение зависит от healthy database.

Приложение наружу не торчит напрямую на весь интерфейс — порт проброшен на localhost сервера, дальше production-инфраструктура уже проксирует его наружу.

В Dockerfile после build приложение запускается не root-пользователем.

Это всё небольшие вещи, но вместе они делают deploy намного более предсказуемым, чем «зайти на сервер по SSH и npm start».

---

## SECURITY

После тестов отдельно появился security workflow.

Там:

- dependency audit;
- CodeQL;
- Dependabot.

И здесь сразу стало видно, зачем security scanner вообще нужен.

Например, CodeQL ругнулся даже на E2E-код, где URL Яндекса проверялся через:

```ts
url.includes("yandex.net")
```

Проблема: строка `yandex.net.evil.example.com` тоже это содержит.

Для тестового фильтра это не «взлом production», но замечание по сути правильное: если речь про host — проверять надо hostname, а не случайный substring.

Исправил через `new URL(...).hostname`.

---

## DEPENDABOT

Dependabot сначала выглядит как бот, который внезапно захламил Actions.

Он создаёт PR на обновления зависимостей.

После того как CI начал запускаться на каждый PR, каждый Dependabot PR тоже начал получать полный CI + Security.

Сначала это выглядит как тонна лишних запусков.

Но смысл правильный: обновление зависимости — тоже изменение кода окружения.

Особенно когда бот предлагает что-то вроде Prisma `6 → 7` или ESLint `9 → 10`.

Если такой PR красный — это не проблема production.

Это буквально означает:

«С этой новой версией проект сейчас не проходит проверки. Не merge».

И как раз здесь CI работает так, как должен.

## COVERAGE

Coverage есть как отдельная команда.

Но я пока специально не делаю из процента coverage главный KPI проекта.

100% coverage не означает 100% нормального поведения.

Мне важнее, чтобы были покрыты места, где реально есть риск:

- data mapping;
- authorization;
- transactions;
- uploads;
- forms;
- public routes;
- critical E2E.

Если когда-нибудь coverage станет командным quality gate — тогда уже имеет смысл договариваться о threshold как о правиле команды.

## ЧТО ТЕСТЫ РЕАЛЬНО НАШЛИ

Самая полезная часть всей этой истории — тесты реально нашли ошибки, а не просто стали зелёной декорацией в GitHub.

Из найденного:

- неправильная env-переменная upload limit;
- потеря localized fields;
- commits update без нормального удаления старых;
- `requireAdmin()` без `await`;
- операции replace без transaction;
- `closeOverlay` не возвращал body scroll;
- loading button оставалась кликабельной;
- `disabled` не везде доходил до настоящего input;
- DecorButton плохо соответствовал semantics обычной кнопки;
- client/server validation контактов расходилась;
- форма очищалась даже после ошибки отправки.

После этого отношение к тестам стало немного другим.

Изначально я добавлял их во многом потому, что хотел показать умение работать с тестированием.

В итоге они реально заставили исправить production-код.

## AI И ТЕСТЫ / РЕФАКТОР

Большая часть проекта писалась мной самостоятельно.

Рефактор, анализ и большой тестовый набор я делал с сильной помощью нейронки.

Для себя решил так: мне нет смысла вручную писать десятки почти одинаковых test cases только ради морального права сказать «всё напечатал сам».

Но есть другое правило:

Если код лежит в моём проекте — я должен понимать, зачем он там.

Поэтому тесты я запускал, разбирал, почему они падают, смотрел, где тест действительно нашёл баг, а где проблема была в самом тесте / окружении.

Для меня это оказалось полезнее, чем слепо писать большое количество boilerplate.

## ЧТО Я СЕЙЧАС СДЕЛАЛ БЫ ИНАЧЕ

Если бы я начинал Sadovnikov с текущими знаниями:

### 1. Меньше собственной инфраструктуры вокруг UI

Не каждую маленькую вещь надо превращать в свою систему.

Tooltip, breakpoint, typography — часть решений можно было сделать проще.

### 2. Раньше определил бы границы Server / Client

Переезд на Next заставил часть старой архитектуры переделывать именно потому, что она была построена до понимания этих границ.

### 3. Раньше добавил бы БД и admin

Mock data хорошо для старта, но после определённого размера проекта начинает мешать.

### 4. Раньше добавил бы несколько критичных тестов

Не весь нынешний suite.

Но auth / mappings / uploads / contact form — точно стоило закрепить раньше.

### 5. Не пытался бы добавить каждый модный инструмент

Visual regression, Lighthouse CI, k6 были хорошими экспериментами.

Но «я умею подключить инструмент» и «этому проекту нужен инструмент» — разные вещи.

Наверное это один из самых полезных выводов последних итераций.

---

## ЧТО ОСТАВЛЮ КАК ЕСТЬ

Не хочу бесконечно рефакторить проект до абстрактного идеала.

На каком-то этапе надо уметь сказать: эта часть нормальная, работает, тестируется — всё.

Иначе pet-project превращается в вечную стройку.

Сейчас основная задача Sadovnikov — быть портфолио и показывать, что я умею довести приложение до production, а не доказать, что я способен бесконечно менять архитектуру.
